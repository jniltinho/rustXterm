## Tab switch during remote video (release, 4 CPUs)

Tests: `crates/ui/src/lab_gates.rs` `lab_gates::ui_gate_tab_switch_during_rdp_video` and
`lab_gates::ui_gate_tab_switch_during_vnc_video`. The real engine is the UI backend; two tabs (SSH to
`alice@2222` and the desktop). The test clicks into the remote xterm and types
`while true; do find /usr; done` as `DesktopInput` key events, so the xterm scrolls continuously
("video"). For 20 s it alternates `SelectTab` between the two tabs and times `step()` + `render()` of
the next frame, then steps frames for 150 ms. Throughput counts the framebuffer dirty rectangles the
UI consumed while the desktop tab was visible (hidden tabs receive no updates by design). Ctrl-C stops
the loop at the end.

| Measurement | n | p50 | p95 | max | Limit | Result |
|---|---|---|---|---|---|---|
| RDP (xrdp): tab switch to next frame built and rendered | 128 | 5.67 ms | 7.12 ms | 79.04 ms | p95 ≤ 100 ms | pass |
| VNC (TigerVNC): tab switch to next frame built and rendered | 129 | 5.75 ms | 6.90 ms | 53.73 ms | p95 ≤ 100 ms | pass |

Remote activity while visible (proves the remote was busy; the test asserts ≥ 1 Mpx/s):

| Protocol | Updates (rects) | Pixels | Visible time | Rate |
|---|---|---|---|---|
| RDP | 823 | 126,079,626 | 9.6 s | 86 updates/s, 13.13 Mpx/s (~16 full 1024×768 screens/s) |
| VNC | 24,057 | 77,386,384 | 9.6 s | 2,506 updates/s, 8.06 Mpx/s |

An earlier release run gave the same picture (RDP p95 6.64 ms, VNC p95 7.65 ms). Debug build
(`cargo test -p rxt-ui --lib lab_gates -- --ignored`, all three UI gates): RDP p95 11.04 ms
(7 updates/s, 6.82 Mpx/s; the unoptimized RDP decoder delivers fewer, larger rectangles), VNC p95
12.77 ms (2,482 updates/s). The threshold is asserted on optimized builds only, like M1; the
busy-remote check is asserted in both.

## Windows NLA receipt (manual, pass)

Tests: `crates/rdp/tests/vm_rdp.rs` (`#[ignore = "windows-vm"]`), against the VM above.

- `rdp_windows_nla_login_input_and_resize`: prompts in order `CertificateUnknown`
  (`CN=WIN-09FTP9U6TPL`, port 53389) then `Password` for `vagrant`, so no credentials before trust;
  CredSSP/NLA (NTLM) logon; `Resized 1024×768`; first `Update` after ~0.3 s; Super_L and Escape key
  events each produced screen updates; a display-control request for 1280×720 produced
  `Resized 1280×720` (1.36 s on the first run after boot, 0.07 s on the second) followed by a
  full-screen `Update`.
- `rdp_windows_nla_wrong_password_fails_in_credssp`: a wrong password fails inside CredSSP
  (`STATUS_LOGON_FAILURE [0xc000006d]`) before any desktop exists, which shows the server enforced NLA
  (TLS-only security would have reached the logon screen).

No `crates/rdp` changes were needed. The VM was halted (not destroyed) afterwards.

## Deviations

- xrdp 0.9.24 accepts the Display Control channel but does not resize; resize is proven by the Windows
  receipt and by the hostile-peer reactivation test (`hostile_rdp::reactivation_resizes_and_rejects_oversized`).
- xrdp in the lab uses TLS security, not NLA; CredSSP/NLA is proven only by the Windows VM receipt,
  which is manual and not part of `lab/lab.sh test`.
- Active FTP cannot work through Docker port publishing (the `PORT` address would be the container's own
  loopback), so the active test reaches the `ftp` container directly through the bridge gateway.
- VNC framebuffers and rectangles are capped at 8192 px per edge and 8,294,400 pixels (vnc-rs limit),
  enough for 3840×2160.
- As in M1, tab switch is timed in the egui_kittest harness (programmatic `SelectTab`, `step()` +
  `render()` with lavapipe readback), not a real window with vsync; frames between samples were built
  without rendering. The "video" is a scrolling xterm, not a media player; the throughput table shows the
  update rate actually delivered.
