## Context

- The platform seam already supports two adapters: `apps/rustxterm/src/os.rs` picks `rxt-platform-linux` or `rxt-platform-windows` per target; `crates/platform` holds the contracts (paths, theme, clipboard, notifications, dialogs, keyring, control transport, opener, serial).
- The Linux adapter (~1,400 lines) is mostly portable Unix code: the control socket checks the peer with `UnixStream::peer_cred()` (available on macOS through the standard library and tokio), serial uses `serialport`, dialogs `rfd`, clipboard `arboard`, notifications `notify-rust`. Linux-only parts are the Secret Service keyring (`oo7`), the XDG portal theme (`ashpd`) and the `.desktop` entry.
- Unix-only code outside the adapter is already behind `cfg(unix)` (modes 0600/0700 in `store` and `engine`, SSH agent socket, X11 over Unix sockets), so it applies to macOS unchanged.
- Builds are Docker-only. macOS cannot follow that rule: the Apple SDK is licensed for Apple hardware only, `cargo-zigbuild` lacks the AppKit/Metal/Security frameworks the app links to, and `osxcross` would need the SDK inside a Docker image. The macOS build therefore runs natively on macOS. **The authoritative validation host is a hosted GitHub macOS arm64 runner** (`macos-15`): that is where the target (`aarch64-apple-darwin`) is built, clippy/tests/`--self-test` run, and a release is gated. A **disposable local macOS KVM VM is an optional developer convenience only** for contributors without a Mac (mirroring the Windows Vagrant VM under `lab/`); it never gates CI, never ships artifacts. Running macOS under KVM on non-Apple hardware is outside Apple's licence (operator's decision); the end-to-end release receipt still needs a real Mac.
- **The KVM VM is x86_64, not Apple Silicon.** osx-kvm / ultimate-macOS-kvm run `qemu-system-x86_64` (an Intel macOS guest); KVM on an x86_64 host cannot virtualize an ARM guest, so the VM can never execute or render-verify the `aarch64-apple-darwin` artifact. Its role is limited to fast, non-graphical local iteration: editing, `cargo check`/`clippy`/non-graphical `cargo test` for `x86_64-apple-darwin`, and bundle-script shakeout over SSH. Target (ARM64) build, graphics/Metal verification and the receipt all happen on Apple Silicon (the CI runner or a real Mac).

## Goals / Non-Goals

**Goals:**
- `aarch64-apple-darwin` build of the existing app with feature parity to Linux phase 1 (SSH, SFTP, FTP/FTPS, RDP, VNC, Telnet, Serial, agent control).
- No `unsafe` code; no new crate layer; protocol, engine and UI crates untouched except for `cfg` where needed.
- A required CI/release `macos` job on a hosted macOS arm64 runner (the authoritative validation host); `MACOSX_DEPLOYMENT_TARGET=13.0`; `.app` in `.dmg` and `.tar.gz`, ad-hoc signed by default.

**Non-Goals:**
- Intel or universal binaries, macOS < 13, App Store/sandbox, local shell, Homebrew cask (all later).
- Cross-compiling macOS from Linux.

## Decisions

1. **Separate crate `crates/platform-macos`**, mirroring the Windows adapter, rather than turning `platform-linux` into a Unix crate. The modules that are identical in substance (control socket, serial) start as adapted copies of the Linux ones. Alternative (shared `platform-unix` crate) adds a layer for ~600 lines; revisit if the copies drift.
2. **Keychain through `security-framework`** (generic password, service `rustxterm`, account `rustxterm:<id>`), the safe API, so the crate keeps `unsafe_code = "forbid"`. Alternative `keyring` crate: an extra abstraction over the same calls.
3. **Theme through an independent watcher behind `ThemeSource`**, not eframe events. The UI reads appearance only via the `ThemeSource` contract (`crates/ui/src/app.rs` gets Light/Dark from it; there is no eframe→adapter bridge, so the earlier "theme from winit" assumption was wrong). The macOS adapter therefore reads `AppleInterfaceStyle` and reports changes the same way the Linux adapter reports portal changes — a background watcher on a `KVObserver`/distributed-notification for `AppleInterfaceStyleSwitchesAutomatically`/`AppleInterfaceStyle` via `security-framework`/`core-foundation` safe wrappers, or, if no safe notification path is viable, a short poll of the value. No eframe coupling, no `unsafe`.
3b. **Native dialogs via `rfd`'s async main-window API**, not the synchronous parented pattern. `dialog_parent` (`crates/ui/src/app.rs:2761`) drops the raw AppKit window handle, and reconstructing one from the string seam would need `unsafe` — which this crate forbids and which must not silently extend the Windows exception. So macOS uses `rfd`'s async `AsyncFileDialog`/message dialog with `set_parent`/main-window selection (safe, sheet-attached) where a parent is needed, and the plain async dialog otherwise. Sheet attachment is checked in the receipt. If a native AppKit touch (menu, window tweak) is ever needed, the safe `objc2`/`objc2-app-kit` route keeps `unsafe_code = "forbid"` — [photocraft's `mac_window.rs`](https://github.com/storytold/photocraft/blob/HEAD/apps/photocraft/src/mac_window.rs) does exactly this ("All safe objc2 calls", `MainThreadMarker`).
4. **Paths** from `dirs` (`data_dir` = `~/Library/Application Support`, `cache_dir`, logs under `~/Library/Logs`); runtime directory for the control socket: `$TMPDIR/rustxterm-<uid>` (per-user `TMPDIR` on macOS, mode 0700, checked as on Linux).
5. **Serial**: `serialport` enumeration filtered to `/dev/cu.*`; the matching `/dev/tty.*` entries are dropped.
6a. **macOS test VM (osx-kvm / ultimate-macOS-kvm) — x86_64, dev-only, non-graphical.** A disposable VM under `lab/macos/` built from [osx-kvm](https://github.com/kholia/osx-kvm) (`boot-macOS-headless.sh`, a QEMU/KVM/OpenCore setup) or [ultimate-macOS-kvm](https://github.com/Coopydood/ultimate-macOS-kvm). Both run `qemu-system-x86_64` — an **Intel macOS guest**; KVM on an x86_64 host cannot virtualize an ARM guest, so the VM runs `x86_64-apple-darwin` and **cannot build, execute or render-verify the `aarch64-apple-darwin` target**, and its OpenCore setup has **no Metal-capable GPU**, so it cannot run the UI snapshot tests either (which are Linux-gated anyway — `crates/ui/src/tests.rs:188`). Its only role is fast local iteration without a Mac: `cargo check`/`clippy`/non-graphical `cargo test` for the x86_64 target and bundle-script shakeout over SSH, driven like `lab/vagrant/windows` by a `rxt.sh` (`push`, run, screenshot). A `lab/macos/README.md` records the create/destroy recipe, pinned guest macOS version and tool commit, the fictional guest account and the forwarded SSH port; the VM image is never committed, never in a Docker build context, never distributed, and **never gates a release**. Target (ARM64) build, Metal/graphics verification and the receipt all require Apple Silicon (the CI runner or a real Mac). Alternative: a hosted macOS runner (licence-clean, paid) or a borrowed Mac.

6. **Packaging** in a small script (`packaging/macos/bundle.sh`) run on the Apple-Silicon host: `Info.plist` (bundle id `io.github.jniltinho.rustxterm`, version from the workspace, `LSMinimumSystemVersion` 13.0, `NSHighResolutionCapable`), `.icns` built from the existing 1024/512/256 px PNGs with `iconutil`, `codesign --sign -` (ad-hoc) or Developer ID with `--options runtime` when secrets exist, `hdiutil create` for the `.dmg`, `notarytool` + `stapler` when secrets exist. **`Info.plist`'s `LSMinimumSystemVersion` alone does not control the binary's minimum OS**, so the build also exports `MACOSX_DEPLOYMENT_TARGET=13.0` for both the Rust compile and any native (`cc`) compile, and records the selected SDK/toolchain in the receipt.
7. **CI/build**: the macOS steps (pinned toolchain from `rust-toolchain.toml`, `MACOSX_DEPLOYMENT_TARGET=13.0`, `cargo clippy --locked -D warnings`, `cargo test --locked` with lab tests `#[ignore]`/Linux-gated, the render smoke test, `--self-test`, and the bundle/dmg step with `dist-check`: `otool -L` allowlist, bundle layout, checksums, Mach-O arch (`arm64`) and min-version check, guard). **The authoritative host is the hosted macOS arm64 runner (`macos-15`)** — the only place the ARM64 target is built and the graphics/`--self-test` run. Following photocraft's model (which keeps its scarce macOS runner slots for releases — [ci.yml](https://github.com/storytold/photocraft/blob/HEAD/.github/workflows/ci.yml): "macOS is tested only by release.yml"), the macOS job **lives in `release.yml`** and is the gate for the macOS artifacts: a failing macOS build/test blocks shipping those artifacts, and a `workflow_dispatch` lets a maintainer run it on demand before tagging. This keeps `ci.yml` (per-push, Docker/Linux) cheap. The **x86_64 KVM VM is dev-only** and runs the non-graphical subset locally (compile/clippy/non-graphical tests for `x86_64-apple-darwin`) before tagging. When the hosted runner is unavailable for a repo, macOS simply is not published for that release (Linux/Windows-only release, see spec). The toolchain is installed only inside the VM or the runner, never on a developer desktop.
8. **Receipt — build-once, test, promote** (not Windows' rebuild model). macOS packaging/signing is not byte-reproducible, so the Windows "rebuild and match checksums" receipt does not apply. Instead: the Apple-Silicon host builds the artifacts **once**, runs the gates and the end-to-end checks against *those* artifacts, writes `docs/gates/macos.md` binding the commit to the **checksums of the exact artifacts tested** (plus SDK/toolchain, Mach-O arch+min-version), and those immutable artifacts are the ones promoted to the release — `release.yml` does not rebuild them. Signing/notarization order: `codesign` the `.app` → build the `.dmg` → `codesign` the `.dmg` → `notarytool submit --wait` → `stapler` (receipt records the stapled hashes). The macOS receipt gate is machine-checkable (`dist-check` verifies the release artifacts' checksums equal the receipt's). Note: the current `release.yml:116` ships Windows artifacts even without a passing receipt — the macOS path does **not** copy that; no covering receipt ⇒ no macOS artifacts.

## Risks / Trade-offs

- **Runner availability/cost** → macOS minutes on a private repository bill at 10× Linux. Mitigation: the local KVM VM is the default build/test host (no CI minutes needed), and the optional hosted `macos` job runs only on `main`/tags with a cached `target/`.
- **KVM VM licence and fragility** → running macOS under KVM on non-Apple hardware is outside Apple's licence (operator's decision; never in CI or artifacts), and OpenCore/osx-kvm setups can break on macOS updates. Mitigation: pin the guest macOS version and the osx-kvm/ultimate-macOS-kvm commit in `lab/macos/README.md`, keep the licence-clean paths (hosted runner, real Mac) documented, and keep the real-Mac receipt as the release gate.
- **No local verification** → developers without a Mac cannot reproduce macOS failures. Mitigation: keep macOS-specific code small and in one crate; every CI failure log is the reference; the receipt needs someone with a Mac.
- **Gatekeeper on unsigned builds** → users see "cannot be opened because the developer cannot be verified". Mitigation: ad-hoc signature, release-note instructions; Developer ID + notarization (Apple Developer Program, user decision and cost) removes the prompt.
- **Reproducibility** → macOS linker output and signatures are not bit-for-bit reproducible across runner images. Trade-off: checksums are published, reproducibility is only required for Linux and unsigned Windows artifacts.
- **Graphics** → wgpu uses Metal on macOS, and the UI snapshot tests are Linux-gated (`crates/ui/src/tests.rs:188`), so neither the x86_64 KVM VM (no Metal GPU) nor the pixel-diff suite verifies macOS rendering. Mitigation: headless build/test checks are kept separate from the graphics gate; a dedicated **macOS render smoke test** (window opens, one frame drawn on a real Metal device) runs on the Apple-Silicon runner and is part of the receipt — it is never claimed from the VM.
