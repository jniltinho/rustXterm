## Context

See proposal.md - Why. Current state (base change D1, D8, D10, D12, D14):

- `crates/platform` defines `Paths`, `ThemeSource`, `Clipboard`, `Notifier`, `FileDialogs` (+`set_parent`), `Keyring`, `ControlTransport` (`listen`/`connect` with framed streams), `Opener`, `SerialPorts`; `fake.rs` implements all of them for tests.
- `crates/platform-linux` uses `dirs` (XDG), `ashpd` (portal theme and file chooser) with `rfd` fallback, `arboard`, `notify-rust` (D-Bus), `oo7::dbus` (Secret Service), a Unix socket in `$XDG_RUNTIME_DIR/rustxterm/` checked with SO_PEERCRED, `xdg-open`, and sysfs + `serialport` for serial.
- Only `apps/rustxterm` depends on the adapter (`agent` and `serial` use it as a dev-dependency); `cargo xtask layers` enforces it with a `LINUX_ONLY` crate list.
- Unix-only code outside the adapter: `store/db.rs` and `store/envelope.rs` (`OpenOptionsExt::mode(0o600)`, `set_permissions`), `engine/workspace.rs` (`DirBuilderExt::mode(0o700)`), `ssh/handler.rs` agent forwarding over `SSH_AUTH_SOCK` (`cfg(unix)`), `ssh/lib.rs` `AgentClient::connect_env`, `ssh/x11.rs` Unix display socket (`cfg(unix)` with a TCP path already present), `ui/file_tab.rs` mode display (already cfg'd), and tests using `std::os::unix`.
- Build: Docker image (Ubuntu 24.04 by digest + snapshot apt, Rust 1.99 from checksummed tarballs, zig + cargo-zigbuild), `cargo fetch` as the only networked stage, `--network=none` build. Statically linked SQLCipher + vendored OpenSSL (also used directly for legacy RDP TLS). Workspace lint `unsafe_code = "forbid"`.

## Goals / Non-Goals

**Goals:**
- Same features on Windows as on Linux for SSH, SFTP, FTP/FTPS, RDP, VNC, Telnet, Serial, store and agents, with no change to protocol, engine or UI logic beyond the cfg points listed above.
- Keep "builds only in Docker" and reproducible pins; no toolchain on the desktop.
- Windows release artifacts produced by the same release workflow.

**Non-Goals:**
- aarch64 (the design keeps it reachable: same crates, a second target later), local shell (delivered by `add-local-shell`), MSIX/Store, a portable data-next-to-exe mode, Windows-specific snapshot images.

## Decisions

### W1. Target and toolchain: `x86_64-pc-windows-gnu`, cross-compiled in Docker

Target Windows 10 1809+, Windows 11 and Windows Server 2019+ with desktop experience (same NT 10 APIs), x86_64. Options evaluated:

| | `x86_64-pc-windows-gnu` (mingw-w64 in Docker) | `x86_64-pc-windows-msvc` via `cargo-xwin` | MSVC on a Windows host |
|---|---|---|---|
| Docker-only | yes, mingw-w64 from the pinned Ubuntu snapshot | yes, but downloads MSVC CRT + Windows SDK at build time | no |
| Licensing | GPL toolchain, runtime pieces have exceptions/permissive | must accept the Microsoft MSVC/SDK license; the image must not be redistributed | normal |
| Reproducibility | apt snapshot + checksummed Rust std | Microsoft manifest URLs/versions drift; must be mirrored and checksummed by us | runner image drift |
| SQLCipher + vendored OpenSSL | `openssl-src` has a `mingw64` target and cross-builds with `x86_64-w64-mingw32-gcc` | `openssl-src` for MSVC drives `nmake`/`cl`; cross from Linux needs `clang-cl` + `llvm-lib` shims, fragile | works |
| `ring` / `aws-lc` | `ring` (our only provider: russh, rustls; `aws-lc` is not built) supports windows-gnu | supported | supported |
| Debugging | DWARF; no PDB | PDB | PDB |

Decision: windows-gnu. It reuses the existing image model (snapshot apt, checksummed Rust components) and avoids the OpenSSL-on-MSVC cross build, which is the biggest risk. Link with `-static` (libgcc, winpthreads) so the exe imports only system DLLs; `xtask dist-check` asserts the DLL import allowlist with `objdump -p`. Deterministic PE: `-Wl,--no-insert-timestamp`, `SOURCE_DATE_EPOCH`. The cross toolchain is a separate `windows-toolchain` Docker stage on top of the Linux `toolchain` stage (mingw-w64 `gcc`/`g++`/`binutils`, including `windres`, from the same snapshot; Rust std for the target checksummed in `docker/rust-components-windows.sha256`), so the Linux image and its cache stay unchanged. W1 spike result (2026-10-13): `cargo clippy --target x86_64-pc-windows-gnu --workspace --all-targets` builds `openssl-sys` (vendored, `mingw64`), `libsqlite3-sys` (bundled SQLCipher), `ring` and `wgpu` with the snapshot mingw-w64 GCC; `aws-lc` is not in the Windows build graph (rustls/russh use `ring`), so no fallback was needed. `cargo-zigbuild` also targets windows-gnu; it is kept as the fallback if mingw-w64 GCC from the snapshot fails on a C dependency (OpenSSL assembly is the expected trouble spot). The MSVC route stays the documented alternative if a dependency ever requires MSVC.

wgpu on Windows uses DX12 first, then Vulkan, then GL (WGL); no runtime library is shipped. eframe's `wayland`/`x11` features are Linux-only no-ops on Windows (checked in W1 build). W1 smoke finding: on GPU-less machines (the VirtualBox VM without 3D) DXGI lists a non-software WARP adapter that owns the display output next to the software WARP adapter; wgpu-hal 30 drops the former and DX12 presentation from the latter leaves the window black. `vendor/wgpu-hal` (`[patch.crates-io]`, 3-line change in `should_keep_adapter`, `vendor/README.md`) keeps the output-owning WARP adapter; headless machines are unaffected and no VirtualBox 3D acceleration is required.

### W2. Unsafe policy (user decision)

`unsafe` is allowed only in `crates/platform-windows`, for direct Win32 calls through the `windows` crate. Mechanics:
- A crate-level `#![allow(unsafe_code)]` cannot relax a `forbid` inherited from `[workspace.lints]`, so `platform-windows/Cargo.toml` declares its own `[lints]` table: the workspace rules copied, `unsafe_code = "allow"`, and clippy `undocumented_unsafe_blocks = "deny"`, `multiple_unsafe_ops_per_block = "deny"`. Every `unsafe` block carries a `// SAFETY:` comment.
- `cargo xtask layers` reads the root and member manifests and fails when: the root `[workspace.lints.rust]` no longer has `unsafe_code = "forbid"`; any crate other than `rxt-platform-windows` lacks `lints.workspace = true` or sets its own lints; the adapter's own table drops or weakens any other workspace lint (each must appear with the same level), sets `unsafe_code` to anything but exactly `"allow"` (the only exemption), or drops the `undocumented_unsafe_blocks`/`multiple_unsafe_ops_per_block` denials. Each violation kind has a manifest-fixture unit test, and a positive fixture proves the intended adapter table passes.
- Clippy for the Windows target runs in CI (W10); compilation alone would not enforce the safety-comment lint.
- Unsafe stays inside small private functions (pipe security descriptor, SID checks, Credential Manager, DACLs, registry notify, HWND parent) with safe wrappers; no `unsafe` type escapes the crate.
- Safe crates are still preferred where they exist and fit: `arboard`, `rfd`, `notify-rust`, `serialport`, `dirs`, tokio named pipes.

### W4. Agent control: named pipe restricted to the current user

Pipe `\\.\pipe\rustxterm-<user SID>-control`, created with `tokio::net::windows::named_pipe::ServerOptions` and a security descriptor whose protected DACL grants access only to the current user SID (`D:P(A;;GA;;;<SID>)`, no inheritance, no Everyone/Users entries).

**Instance lifecycle.** Startup exclusivity and accepting are separate steps. `listen` creates the *first* instance with `first_pipe_instance(true)` (`FILE_FLAG_FIRST_PIPE_INSTANCE`): if the name already exists — another instance of ours, or a squatter of any user — creation fails, `listen` reports "agent control could not start" and nothing is served. Every later instance is created without that flag but with the same descriptor and `reject_remote_clients(true)`, and it is created *before* the connected instance is handed to the engine, so while control is enabled the server always owns at least one listening instance and the name is never free. Another user cannot add instances: creating one needs `FILE_CREATE_PIPE_INSTANCE`, which only our SID holds. Disabling control drops the listener (its listening instance closes, so the name disappears once in-flight connections end); the engine's cancellation token closes in-flight connections. The client retries `ERROR_PIPE_BUSY` for at most 5 s, then fails; `ERROR_FILE_NOT_FOUND` → `Error::NotFound` ("not running").

**Client authentication (server side).** The identity checked is the connection's own security context, not the client's primary process token:
1. Bounded pre-authentication: after `ConnectNamedPipe` the server reads exactly the 4-byte frame length (Windows allows impersonation only after data was read), with a 5 s timeout; nothing is parsed or executed before step 3. A timeout or EOF closes the instance.
2. Synchronously on the same thread, with no `.await` in between: `ImpersonateNamedPipeClient` → `OpenThreadToken(TOKEN_QUERY, OpenAsSelf = TRUE)` → `RevertToSelf`. If `RevertToSelf` fails the process aborts (it must never keep running impersonated).
3. The token passes only if: its user SID equals ours; it has no restricting SIDs (`IsTokenRestricted`); it is not an AppContainer token (`TokenIsAppContainer`); its integrity level is at least the server's (`TokenIntegrityLevel`); and it is not more filtered than the server's token: no group that is enabled in the server's token is deny-only in the client's (`TokenGroups`, `SE_GROUP_USE_FOR_DENY_ONLY`). An ordinary UAC-filtered (non-elevated) token therefore talks to a non-elevated server (both have the same deny-only Administrators group), while a sandbox that disabled groups (deny-only SIDs) is refused. Elevation matrix: because the client applies the same policy to the server (below), the CLI and the GUI must run at the same elevation; a non-elevated CLI and an elevated GUI (refused by the server) or an elevated CLI and a non-elevated GUI (refused by the client) get "agent control runs at a different elevation", never a silent fallback. Removed privileges alone are accepted: control commands need no privileges, so privilege filtering does not widen what a client can do. Any API failure (including an anonymous level whose token cannot be opened) refuses. A refused instance is closed without a response and logged; the buffered 4 bytes of an accepted client are replayed to the frame reader.

**Server authentication (client side).** The client opens the pipe with `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION` (the server may identify but not act as the client), then checks the server with `GetNamedPipeServerProcessId` → the server process token must pass the same policy as a client token (same user SID, no restricting SIDs, not AppContainer, integrity not below the client's, not more filtered), so a lower-integrity or sandboxed process of the same user that created the name while rustXterm was not running is refused ("control pipe is not served by rustXterm of this user"). (Here the process token is the right context: a server cannot impersonate its client to create the pipe.)

Framing (`control.rs`, 1 MiB frames) and the "exists only while enabled" rule are unchanged.

Rejected: AF_UNIX sockets on Windows (no tokio/std support, no peer credentials); TCP loopback (network socket, forbidden by the spec); default pipe DACL (Everyone gets read access); client-PID process-token check on the server (does not reflect the connecting thread's impersonation context or restrictions).

### W5. Two executables on Windows

A GUI-subsystem exe opens no console but cannot print to the terminal that launched it; a console-subsystem exe flashes a console window for GUI starts. Same `apps/rustxterm` crate, two `[[bin]]` targets sharing `main`: `rustxterm.exe` (GUI subsystem) and `rustxterm-cli.exe` (console: CLI, `mcp`, `--self-test`; `src/bin/rustxterm-cli.rs` includes `main.rs` as a module). On Linux the release ships one binary as before (the `rustxterm-cli` target there only prints a pointer to `rustxterm` and is not packaged). Rejected: `AttachConsole(ATTACH_PARENT_PROCESS)` in one GUI exe (shell prompt returns before output, stdin is broken for `mcp` in interactive shells). The GUI subsystem is set per binary from the app's build script (`-Wl,--subsystem,windows` for `rustxterm` only), so `main.rs` stays shared. Resources (icon, version info, manifest with `longPathAware`, UTF-8 active code page, per-monitor DPI v2, common controls v6, `asInvoker`) are compiled by the same build script with mingw `windres` and linked into both exes (no extra crate); the `.ico` is generated from the 256 px PNG.

### W6. Data protection instead of file modes

Unix modes have no meaning on Windows. `Paths::make_private(dir)` (default no-op; Unix keeps its per-file 0600/0700 modes) does on Windows, in order, failing closed and naming the path on any error:
1. **Eligibility:** paths are compared after normalization (verbatim `\\?\` prefix removed, except `\\?\UNC\`, trailing separators trimmed, case-insensitive as NTFS lookups are); the directory's canonical path (`std::fs::canonicalize` of the nearest existing ancestor plus the missing tail, so links and junctions in ancestors are resolved) must equal its absolute path (no link or junction anywhere in the ancestry) and must lie inside the canonical user profile directory (`%USERPROFILE%`) (decision taken in review round 3; locations outside the profile, such as `D:\data`, are rejected). Every existing ancestor from the directory's parent up to and including the profile directory must be safe against other users: owner = the user, Administrators or SYSTEM; a DACL present and not null (`NO_ACCESS_CONTROL` grants everyone everything); and no allow-ACE that applies to the object (not inherit-only) grants a principal other than the user, SYSTEM or Administrators any of `DELETE`, `WRITE_DAC`, `WRITE_OWNER`, `FILE_DELETE_CHILD`, `FILE_WRITE_DATA`, `FILE_APPEND_DATA`, `FILE_WRITE_EA` or `FILE_WRITE_ATTRIBUTES` (write data/attributes allow turning an empty ancestor into a junction between check and use), `GENERIC_ALL` or `GENERIC_WRITE` (SDDL rights, including `FA`/`FW` and generic rights, are decoded to an access mask; unknown rights count as unsafe). Otherwise another user could rename or replace the directory or an ancestor (for example a `shared` folder inside the profile that grants Users full control). Then reject UNC paths (`\\server\share\…`, `\\?\UNC\…`), drives whose `GetDriveTypeW` is `DRIVE_REMOTE`, and volumes whose `GetVolumeInformationW` flags lack `FILE_PERSISTENT_ACLS` (FAT/exFAT), checked on the canonical path's volume. The SQLCipher database runs in WAL mode, which does not support network filesystems, and owner-only protection needs persistent ACLs.
2. **No reparse points:** the directory and every entry below it must not be a reparse point (symlink, junction, mount point): rejected, never followed.
3. **Apply:** missing directories (the target and any missing ancestors below the existing one) are created with `CreateDirectoryW` and the owner-only protected descriptor from the start, so there is no window with an inherited ACL. The whole existing tree (target and every descendant) is checked before anything is changed; an entry owned by anyone but the user, Administrators or SYSTEM (an owner implicitly holds `WRITE_DAC`), or whose ACL lets another user modify it (delete, write or append data, write extended attributes or attributes, change permissions or owner, delete children, generic write/all) is rejected, not repaired, because that user may already hold a handle that survives the repair (for example to turn an empty folder into a junction); entries with only extra read access are repaired: owner = current user SID and protected DACL `D:P(A;OICI;FA;;;<SID>)` (inherited by new files and subdirectories).
4. **Verify:** read back owner and DACL of the directory and of every entry; each must have owner = current user (or Administrators, the default owner of files an elevated administrator creates), the protected flag, and allow-ACEs for our SID only.

SYSTEM and Administrators keep access through privileges (backup/take-ownership), as root does on Linux. Callers, both executables, before any I/O in the directory:
- the data directory (default `%LOCALAPPDATA%\rustxterm` or a custom `data_dir`): GUI startup and CLI/`mcp` startup, before settings-dependent store access; failure blocks opening the store with an error naming the directory (DB, `-wal`, `-shm`, envelope, envelope temp file, failure counter, `backups/` all live there);
- the agent workspace when agent control is enabled (GUI): failure keeps agent file transfer off and is reported.
SQLCipher's `cipher_memory_security` (VirtualLock of every SQLite allocation) is off on Windows: the default working-set quota refuses the locks (`ERROR_WORKING_SET_QUOTA`) and the failure path overflowed the stack in WAL mode (W1 finding); key material in Rust memory stays zeroized, and pages at rest stay encrypted. The configuration directory (`%APPDATA%\rustxterm`, settings only, no secrets) keeps the per-user profile ACL, as config files keep the umask on Linux. `store` and `engine/workspace.rs` keep their mode calls under `cfg(unix)`. Atomic envelope replacement uses `std::fs::rename` (`MoveFileExW` with replace semantics); the directory fsync step is Unix-only.

### W7. SSH, X11 and other Unix-only spots

- Agent auth (`ssh/lib.rs`): on Windows, connect to `\\.\pipe\openssh-ssh-agent` (Windows OpenSSH agent, or the pipe named by `SSH_AUTH_SOCK` when set), then Pageant when the pipe is absent (`AgentClient::connect_named_pipe`, then `connect_pageant`; russh 0.64 ships both on Windows through its `pageant` dependency). With neither, agent authentication is skipped.
- Agent forwarding (`ssh/handler.rs`): the same stream source replaces the `cfg(unix)` Unix socket.
- X11 forwarding: TCP displays already work; on Windows `DISPLAY` unset means "no local X server", reported in the tab when X11 is enabled ("start VcXsrv/X410 and set DISPLAY=127.0.0.1:0"). No auto-detection of X servers. Unix display sockets stay `cfg(unix)`.
- XDMCP (`add-xdmcp-sessions`) needs `Xvnc` and Unix sockets: not offered on Windows until that change designs it.
- Remote cwd follow (`/proc` on the remote host) is unaffected.
- Telnet, FTP, SFTP, RDP, VNC: no OS-specific code.

### W8. Layers and guard

- `LAYERS` gains `rxt-platform-windows` (L1). The "only the app may depend on an adapter" rule covers both adapters (dev-dependencies still allowed).
- `LINUX_ONLY` splits into `LINUX_ONLY` (`ashpd`, `oo7`, `zbus`), `WINDOWS_ONLY` (`windows`, `windows-sys`, `raw-window-handle` as direct dependencies) and `ADAPTER_SHARED` (`arboard`, `rfd`, `notify-rust`, `serialport`, `dirs`), each owned by the adapters only.
- Unsafe-lint check from W2.
- `guard` extracts and scans Windows artifacts: zip members and MSI contents (`msiextract`), same digest/home-path/attribution rules.

### W9. Distribution

- Portable zip `rustxterm-<v>-windows-x86_64.zip`: both exes, `LICENSE`, `THIRD-PARTY-LICENSES`, `ATTRIBUTION.md`, README; fixed member order, mtimes from `SOURCE_DATE_EPOCH`, fixed permissions.
- MSI `rustxterm-<v>-x86_64.msi`, per-user install to `%LOCALAPPDATA%\Programs\rustXterm`, Start Menu shortcut, no admin prompt, built in Docker with `wixl` (msitools from the snapshot). The shortcut's AppUserModelID `rustXterm.rustXterm` lives in the `MsiShortcutProperty` table, which `wixl` does not author: the Docker stage inserts that row with msitools' `msibuild` from a checked-in `.idt` file; `msiinfo export` verifies it. Rejected: `cargo-wix`/WiX on a Windows host (breaks Docker-only), MSIX (needs a trusted signature even for sideloading; no Store goal).
- `SOURCE_DATE_EPOCH` = committer time of the source commit (`git log -1 --format=%ct`); for a receipt-only release commit (W10) the receipt's source commit is used, so the release rebuild equals the tested build.
- Deterministic unsigned artifacts: no `*` GUIDs in the `.wxs` (component GUIDs fixed in the source; ProductCode UUIDv5 of the version under a fixed namespace; UpgradeCode fixed); input file mtimes set to `SOURCE_DATE_EPOCH` before `wixl` runs, so the embedded CAB is stable; PE `--no-insert-timestamp`, `--remap-path-prefix` for build paths. `wixl` 0.103 still writes a random PackageCode and current-time summary dates, so a Docker-side normalizer, `xtask msi-normalize` (pure-Rust `msi` crate, pinned and vendored like other dependencies), rewrites the summary information: PackageCode = UUIDv5 of the version, creation/last-saved/last-printed times = `SOURCE_DATE_EPOCH`, fixed creating application; compound-file directory timestamps are written as zero. `xtask dist-check DIR --reproduce OTHER` compares the zip (which holds both exes) and the MSI of two clean builds (`release.yml` builds `dist` twice, the second with `no-cache`) byte for byte; any remaining difference fails the check (no field is excluded from the comparison). W2 notes: wixl 0.103 ignores `Package/@Id`, `InstallPrivileges` and `RemoveFolder/@Directory`, so the PackageCode and summary dates come only from `xtask msi-normalize` (`msi` 0.10 crate); the Linux ELF of two clean zigbuild builds differs (pre-existing, outside this change), so `--reproduce` covers the Windows artifacts only.
- Order of the release pipeline (signed or not): build exes → `dist-check` on the unsigned exes (DLL allowlist, PE timestamp, reproducibility) → if `WINDOWS_SIGNING_PFX` (+ password) exists, Authenticode-sign both exes with `osslsigncode` → package zip and MSI from those exes → sign the MSI → `osslsigncode verify` on the exes extracted from the zip and the MSI and on the MSI → `guard` → `SHA256SUMS` over all final artifacts (Linux and Windows) last. Without the secret the same pipeline skips the two signing steps and the release notes state that the Windows artifacts are unsigned and explain the SmartScreen "unrecognized app" prompt. A failed signature verification fails the release.
- winget manifest: later, once signed MSIs exist (not in this change).

### W10. Testing

- **Workspace on both targets:** `platform-linux` compiles to an empty crate off Linux (its dependencies are `cfg(target_os = "linux")` and `lib.rs` is `#![cfg(target_os = "linux")]`); `platform-windows` builds its pure helpers (names, SDDL read-back check, peer policy, COM-name normalization, error mapping) on every target, so they are unit-tested on Linux too, and its services only on Windows. The app depends on each adapter only for its target. Linux-only tests are gated by `cfg`: the Linux lab tests (`ssh/tests/lab_ssh.rs`, `serial/tests/lab_serial.rs`), the Unix-socket agent tests (`apps/rustxterm/tests/{agent,cli}.rs`, `agent` client/MCP tests on the Unix transport, the `agent_uid_probe` example), symlink escape tests (`engine`), Unix mode assertions (`store`), and the kittest snapshot tests (Linux/lavapipe is the reference).
- **Cross-compiled tests in Docker:** `cargo clippy --target x86_64-pc-windows-gnu --workspace --all-targets -- -D warnings` (this is what enforces `undocumented_unsafe_blocks` for the Windows code), then `cargo test --workspace --no-run --target x86_64-pc-windows-gnu --message-format=json` lists the test executables; they are packed with the app exes as a CI artifact.
- **`windows-latest` job:** downloads the artifact and runs every test exe plus `rustxterm-cli.exe --self-test` with a minimal `PATH`, propagating each exit code; no toolchain is installed or invoked (hosted images ship Rust tools; they are not used). Windows-only tests (`#[cfg(windows)]`) run here: control pipe same-user round trip, repeated and concurrent clients, pipe gone once the listener is dropped (control disabled), second `listen` refused, squatted name refused, refusal of a client thread impersonating a restricted token and of a low-integrity token, frame limit; Credential Manager round trip, blob limit and the "no credential store" → `Unsupported` mapping; `make_private` on a temp dir with pre-existing files carrying explicit ACEs (repaired), a junction inside (rejected), owner/DACL read-back of DB/WAL/SHM/envelope/backup files after a store create; registry theme read; opener on a temp file; COM enumeration (zero ports allowed) and not-found mapping; a WARP render smoke test (`force_fallback_adapter`, asserts the software adapter was selected and one frame rendered).
- **Snapshots:** kittest image comparisons stay authoritative on Linux (lavapipe). Rejected: second snapshot set for WARP (doubles maintenance for font rasterization noise).
- **Lab:** GitHub Windows runners cannot run Linux containers, so no lab in Windows CI. Lab E2E is manual from the existing local Windows Server 2022 VM (`lab/vagrant/windows`, user decision: reuse it instead of a new Windows 11 VM; fictional `vagrant` box account plus a second fictional local user; VirtualBox NAT reaching the host's 127.0.0.1 lab through `10.0.2.2`; GUI driven by a one-shot interactive scheduled task, screenshots from the VirtualBox framebuffer into git-ignored `docs/prints/windows/`). W1 smoke-tests the portable exes there; W3 runs the release-pipeline zip and MSI. Serial uses the VM's COM1 bridged by VirtualBox to a host pty (`socat`), so no virtual-COM driver is needed; device removal is checked with a USB-serial adapter passed through to the VM. Receipt `docs/gates/windows.md`: source commit, Windows build number, SHA-256 of the tested *unsigned* zip and MSI and of both exes, and one row per mandatory check (fixed row ids, see tasks 3.2) with PASS; any FAIL or untested row keeps the gate closed. `xtask windows-receipt --check` binds the receipt to a release: every mandatory row id present and PASS; the receipt's source commit equals the tagged commit, or is an ancestor whose diff to the tag touches only `docs/gates/windows.md` (the receipt commit itself); and the receipt digests equal those of the unsigned artifacts the release just rebuilt (reproducible builds make the rebuild identical to what was tested). Only after that check are the exes and the MSI signed (W9), so the published files are the tested bytes plus signatures. A Windows 11 client VM is optional later and not a gate. The VM is shared with other local projects: it is halted, never destroyed, after each run.
- Wine is not a gate (named pipes, Credential Manager and DACLs are not faithful under Wine).

## Risks / Trade-offs

- [OpenSSL/SQLCipher cross-build fails on mingw] → first W1 task is a build spike; fallback `cargo zigbuild` for windows-gnu; last resort cargo-xwin with mirrored, checksummed MSVC packages (needs a new user decision on the Microsoft license).
- [Unsafe Win32 code bugs] → confined to one crate, `// SAFETY:` per block, small wrappers, integration tests on the Windows runner; reviewed in the W1 batch.
- [Antivirus/SmartScreen flags an unsigned mingw-built exe] → optional signing, checksums, release notes; signing certificate is a user decision outside the code.
- [Named-pipe name squatting by another user] → `first_pipe_instance`, owner-only DACL, server identity check by the client.
- [Toasts silently missing in the portable zip] → notifications are best-effort by spec; MSI sets the AUMID.
- [wgpu driver issues on old Windows 10 GPUs] → DX12 → Vulkan → GL fallback inside wgpu; `--self-test` and the VM smoke cover WARP.
- [Filesystem races in `make_private`] → checks use paths, not handles: a process of the same user (or an administrator) could swap an entry between check and apply. Accepted: such a process already has the user's rights. Other users cannot: every ancestor up to the profile is checked to grant them no replace or permission-change rights (W6).
- [API floor] → running on Server 2022 and the runner image does not prove Windows 10 1809 compatibility; the adapter uses only APIs documented for Windows Vista/7 or earlier (named pipes, Credential Manager, security descriptors, registry notification, ShellExecute), and dependencies' floors (winit, wgpu, rfd) are recorded in the W1 notes. A 1809 run is optional later.
- [Windows-only regressions not caught locally] → developers have no Windows toolchain; the Windows CI job is the gate before push.

## Migration Plan

New platform; Linux users unaffected. Moving sessions between OSes uses the existing export/import. Rollback: uninstall the MSI or delete the zip folder; data stays in `%APPDATA%`/`%LOCALAPPDATA%\rustxterm` and the `rustxterm:*` Credential Manager entries until removed by hand (documented).
